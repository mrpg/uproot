- As of 2026-11-12, `uproot-proofs` (github.com/mrpg/uproot-proofs) tracks these behaviors using targeted formalizations in Lean:
  - Room lifecycle (`UprootProofs/Rooms.lean`): creation, settings, opening/closing, deletion, defaults and restarts; readiness signals; loaded configs; valid, mutually consistent room/session associations and at most one room per session.
  - Room admission (`UprootProofs/Labels.lean` and `Rooms.lean`): readiness and label checks, non-empty required labels, whitelists, label uniqueness, capacity bounds including zero, free join, reentry and free-slot selection/reuse.
  - Participant page requests (`UprootProofs/Pages.lean`): initialization and valid positions; page entry, visibility/skipping and hook order; once-only hooks; forward and Back navigation with app/round/Repeat boundaries; current-form/token checks and stale/foreign submissions; form acceptance, saving, rejection, errors, cleared optional values and preservation of unrelated fields; timeouts; hook-directed moves and reaching the end.
- Changes affecting any tracked behavior must be checked against the formal specification and its proved guarantees in `uproot-proofs`, including the implementation's correspondence to the model and the model's assumptions. Update the model/proofs for intended semantic changes and, from this repository, recheck them with `timeout 300s uv run --project "$PWD" --directory ../uproot-proofs lake build`. A successful proof build alone does not establish correspondence with the Python implementation.
- After such changes, regenerate both snapshots in `tests/cases/` using the instructions in its README, update the recorded `uproot-proofs` commit, and run `./test-models.sh` in full. Lean is needed for proof checks and regeneration, never for `release.sh` or running the stored cases.
- Always run the long case replays with maximum parallelism (one shard per available CPU).
